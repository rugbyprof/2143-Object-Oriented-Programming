part 2 Is It Really “Is-A”? Liskov substitution

Public inheritance is a promise: a derived object can be used anywhere a base object is expected, and the code using it won't notice. This is the Liskov Substitution Principle (LSP), the “L” in SOLID. “A square is a rectangle” is true in geometry. Is it true in code?

class Rectangle {
public:
    virtual ~Rectangle() = default;
    virtual void SetWidth(int width) {
        width_ = width;
    }
    virtual void SetHeight(int height) {
        height_ = height;
    }
    int Area() const {
        return width_ * height_;
    }
protected:
    int width_ = 0;
    int height_ = 0;
};

class Square : public Rectangle {          // keep it square!
public:
    void SetWidth(int width) override {
        width_ = width;
        height_ = width;
    }
    void SetHeight(int height) override {
        width_ = height;
        height_ = height;
    }
};

void Stretch(Rectangle& shape) {           // written by someone who only knows Rectangle
    shape.SetWidth(5);
    shape.SetHeight(4);
    cout << shape.Area() << " ";
}

part 3 Coupling and Cohesion

Coupling is how much one class depends on the insides of another. Keep it low, so a change in one class doesn't break five others. Cohesion is how closely a class's methods belong together. Keep it high: one class, one job. Two guidelines help:

  • Law of Demeter (“only talk to your friends”): call methods on your own members and parameters, not on objects they return. Chains like a.getB().getC().doIt() are a warning sign.
  • Tell, don't ask: instead of pulling data out of an object and deciding for it, tell the object what you want and let it decide.

Here is part of a real FTXUI renderer for a game of War (trimmed slightly). The lambda builds the whole screen:

part 5 Pattern: Strategy swap an algorithm at run time

A design pattern is a named, proven solution to a design problem that keeps coming up. Strategy pulls a decision out into its own class hierarchy, so the object that uses it can switch strategies while running. W07's SortedList<T, Compare> was the compile-time version. This one uses virtual.

class HitStrategy {
public:
    virtual ~HitStrategy() = default;
    virtual bool ShouldHit(int total) const = 0;
};
class Cautious : public HitStrategy {      // hits below 12
public:
    bool ShouldHit(int total) const override {
        return total < 12;
    }
};
class HouseRule : public HitStrategy { /* hits below 17 */ };
class Reckless : public HitStrategy { /* hits below 20 */ };

class Dealer {
public:
    explicit Dealer(unique_ptr<HitStrategy> strategy)
        : strategy_(std::move(strategy)) {
    }
    void SetStrategy(unique_ptr<HitStrategy> strategy) {
        strategy_ = std::move(strategy);
    }
    string Decide(int total) const {
        return strategy_->ShouldHit(total) ? "hit" : "stand";
    }
private:
    unique_ptr<HitStrategy> strategy_;
};

part 6 Pattern: Factory create the right subclass from data

In W06's makeCharacter, a switch picked a subclass. Real programs pick from data: a save file, a config line, a menu choice. A factory keeps the “which class do I new?” decision in one place, so the rest of the program only ever sees the base class.

using Maker = function<unique_ptr<Character>(const string&)>;

unique_ptr<Character> MakeCharacter(const string& kind, const string& name) {
    static const map<string, Maker> registry = {
        {"warrior", [](const string& n) {
             return make_unique<Warrior>(n);
         }},
        {"wizard", [](const string& n) {
             return make_unique<Wizard>(n);
         }},
    };
    auto found = registry.find(kind);
    if (found == registry.end()) {
        return nullptr;
    }
    return found->second(name);
}

// Loading a party from a save file:   wizard Merlin
//                                     warrior Conan
string kind;
string name;
while (save >> kind >> name) {
    party.push_back(MakeCharacter(kind, name));
}

part 7 Pattern: Observer “tell me when something happens”

The game knows when a score changes. A log file, a high-score banner, and an achievement tracker all care. If the game called each of them directly, it would be coupled to all of them. Instead, the subject keeps a list of listeners and calls each one when something happens. It never knows what they do.

class ScoreBoard {
public:
    using Listener = function<void(const string&, int)>;
    void Subscribe(Listener listener) {
        listeners_.push_back(listener);
    }
    void Record(const string& player, int points) {
        totals_[player] += points;
        for (const Listener& listener : listeners_) {
            listener(player, totals_[player]);
        }
    }
private:
    map<string, int> totals_;
    vector<Listener> listeners_;
};
ScoreBoard board;
board.Subscribe([](const string& who, int total) {
    cout << "[log] " << who
         << "=" << total << " ";
});
int high = 0;
board.Subscribe([&high](const string& who, int total) {
    if (total > high) {
        high = total;
        cout << "[HIGH " << who << "] ";
    }
});
board.Record("Rhea", 10);
board.Record("Vex", 8);
board.Record("Rhea", 5);
board.Record("Vex", 9);

part 8 Pattern: Facade one simple front door

A facade gives a complicated set of classes one simple interface. Callers talk to the facade only. Here it fixes Part 3's renderer: the game side offers a WarTable that answers one question, “what should the screen show right now?” It answers with a plain TableView struct, so the view never touches Game, Player, or RoundResult again.

struct SeatView {                     // plain data: everything a view needs, nothing more
    string name;
    int cardsLeft = 0;
    string lastCard;
};
struct TableView {
    SeatView left;
    SeatView right;
    string status;
    bool gameOver = false;
};

class WarTable {                      // the facade
public:
    WarTable(const string& leftName, const string& rightName)
        : game_(leftName, rightName) {
    }
    void PlayRound() {
        if (!game_.isGameOver()) {
            last_ = game_.playRound();
        }
    }
    TableView View() const {
        TableView view;
        view.left = Seat(game_.getPlayer1(), last_.card1);
        view.right = Seat(game_.getPlayer2(), last_.card2);
        view.status = Status();
        view.gameOver = game_.isGameOver();
        return view;
    }
private:
    static SeatView Seat(const Player& player, const Card& card);   // fills in one SeatView
    string Status() const;                                         // Question 12
    Game game_;                       // composition: the table owns the game
    RoundResult last_;
};
